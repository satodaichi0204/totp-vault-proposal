技術構成とセキュリティ設計（提案）

2026年10月 版 ／ 対象：Windows 10・11 向けデスクトップアプリ ／ 仕様確定前の提案のため、打ち合わせで調整します

要点

  1. .NET 10（長期サポート、2028年11月まで）+ WPF で開発します。.NET 8・9 は 2026年11月10日にサポートが終わるため、新規開発では選びません。
  2. 保存データは マスターパスワード → Argon2id → AES-256-GCM で暗号化します。データ用の鍵と、それを包む鍵を分けるため、パスワード変更や Windows Hello の追加でデータの再暗号化が要りません。この中心部分は試作済みで、自動テスト 91 件に合格しています。
  3. Windows の暗号化機能（DPAPI）だけには頼りません。同じ Windows ユーザーで動く不正なプログラムに復号されるうえ、別の PC でバックアップを戻せないためです。
  4. Windows Hello（第2段階のご提案）は「確認画面を出すだけ」の形にせず、Windows Hello の鍵で作った値を、データの鍵を守るために使います。確認画面だけでは、画面を飛ばされると保護になりません。
  5. コピーしたコードは、一定時間で消すだけでなく、クリップボードの履歴（Win+V）とクラウド同期にも残しません。あわせて、画面共有・録画にアプリの画面が映らない設定にします。
  6. アプリはインターネットに一切接続しません。外部から攻撃される入口がなく、通信していないことを利用者が確かめられます。
  7. 守れることと、守れないこと（ロック解除中のマルウェアなど）を一覧にしています。

1技術構成と選定理由

項目採用理由
実行環境.NET 10（LTS）サポートは 2028年11月まで。.NET 8（LTS）と .NET 9 は、どちらも 2026年11月10日に終了します。
画面WPF（MVVM）Windows 10 でも安定して動き、実績と情報が多く、保守しやすいです。Windows 11 風の Fluent テーマが使えます。WinUI 3 は見た目は新しいものの、配布の仕組みが複雑で、Windows 10 での不具合情報も多いため見送ります。
暗号.NET 標準（AesGcm、HMAC、乱数）＋ Argon2id暗号処理は自作せず、OS の暗号機能（CNG）を呼ぶ .NET 標準を使います。Argon2id だけは標準にないため、実績のあるライブラリを使います（試作では Konscious、本番では libsodium と速度を比べて決定）。
QR の読み取りZXing.Net画像・クリップボード・画面の取り込みから読み取ります（12章）。
配布自己完結型 ＋ インストーラー.NET を同梱するため、利用者の PC に .NET を入れる必要がありません。x64 と Arm64（Snapdragon 搭載 PC）向けを作れます。
Windows の機能Win32 API・WinRT を直接呼ぶクリップボード履歴の除外、画面キャプチャの除外、Windows Hello、ロックの検知に使います。対象は Windows 10 2004 以降（22H2 を推奨）です。

構成は「画面（WPF）」「アプリの処理」「暗号・TOTP の中核（画面に依存しないライブラリ）」に分けます。中核部分は自動テストで確かめられ、将来ほかの画面（タスクトレイ常駐、コマンドラインなど）を追加しても使い回せます。

3暗号化と鍵の管理

「データを暗号化する鍵（DEK）」と「DEK を包む鍵（KEK）」を分ける、エンベロープ暗号化という方式にします。

方式と、その理由

  • Argon2id（RFC 9106）：パスワードから鍵を作る計算を、わざと重くします（メモリ 64 MiB、3回、並列4。RFC 9106 が推奨する設定の一つ）。GPU を並べた総当たりを、従来の PBKDF2 より大幅に遅くできます。
  • AES-256-GCM：暗号化と同時に改ざんを検知します。1ビットでも書き換えられたファイルは開きません。
  • 鍵を分ける理由：マスターパスワードを変えるときは DEK を包み直すだけで、データ部は1バイトも変わりません。Windows Hello の鍵も、同じ DEK をもう一つ包むだけで追加できます。
  • DPAPI を主役にしない理由：DPAPI は同じ Windows ユーザーで動くプログラムなら誰でも復号でき、別の PC では復号できません。ローカルアカウントで管理者が Windows のパスワードを再設定すると、復号できなくなる場合もあります。

ファイルの形式

magic "TOTPVLT1"（バックアップは "TOTPBAK1"） | 保管庫ID 16B
Argon2id の条件（メモリ量・回数・並列数）| salt 16B
DEK 用 nonce 12B | 包んだ DEK 32B | タグ 16B       ← 改ざん検知の対象：先頭から salt まで
データ用 nonce 12B | タグ 16B | 暗号文             ← 改ざん検知の対象：magic と保管庫ID
  • nonce と salt は保存のたびに乱数で作り直し、使い回しません。
  • ファイルに書かれた Argon2id の条件には上限を設けます。細工したファイルで大量のメモリを確保させる攻撃を防ぐためです。
  • 試作版で、ロック解除にかかる時間は約 1.3 秒でした（検証用の仮想マシン、マネージド実装）。本番では libsodium と比べ、0.5〜1 秒に収まるよう条件を決めます。

4マスターパスワード

  • 初回設定で作ります。長さ（12文字以上を推奨）と強さの目安を、その場で表示します。強さの判定は PC の中だけで行い、外部には送りません。
  • 忘れた場合は、開発者でも復旧できません（裏口を作らないため）。代わりに、初回設定の最後に暗号化バックアップの作成を必ず案内します（11章）。
  • 入力を間違えたときの待ち時間は画面上の対策です。ファイルを盗まれた場合の本当の歯止めは Argon2id の計算コストです。この違いを踏まえて設計します。
  • パスワードは PasswordBox で受け取り、文字列（string）に変えずに鍵の計算へ渡します。

5Windows Hello（第2段階）

依頼文の「対応検討」に対する方式のご提案です。実機での検証に時間をかけるため、第2段階として分けることを提案します（17章）。

採用しない方法

UserConsentVerifier で「本人確認しました」という結果だけを受け取り、ロックを解除する方法。

データの鍵は別の場所（DPAPI など）にあるため、確認画面を飛ばすようにアプリを改変されると、そのまま中身を読まれます。見た目だけの保護になります。

採用する方法

KeyCredentialManager で TPM の中に鍵を作り、決まった値に署名させます。署名結果から HKDF で KEK ② を作り、DEK を包みます。

顔・指紋・PIN で本人確認しないと署名できないため、Windows Hello を通らなければ鍵そのものが手に入りません。

  • 登録時に2回署名し、結果が同じであること（毎回同じ値になること）を確かめてから有効にします。
  • マスターパスワードは予備として必ず残します。PC の交換、Windows Hello の再設定、TPM の初期化で Windows Hello は使えなくなるためです。
  • KEK ② はこの PC 専用です。バックアップには使いません。
  • Windows Hello が使えない PC（顔・指紋の装置がない PC でも PIN は使えます）では、設定画面に表示しません。

6クリップボード

  • 履歴とクラウド同期から除外：コードをコピーするときに、Windows が定める3つの形式（ExcludeClipboardContentFromMonitorProcessing、CanIncludeInClipboardHistory = 0、CanUploadToCloudClipboard = 0）を一緒に書き込みます。単に消すだけでは、Win+V の履歴や他の PC にコードが残るためです。
  • 自動消去：既定は 20 秒後（設定で変更可）。消す前にクリップボードの更新番号（GetClipboardSequenceNumber）を確かめ、利用者が後から別のものをコピーしていたら消しません。
  • ロックしたとき、アプリを終了したときにも、アプリが入れたコードが残っていれば消します。
  • コードは 30 秒前後で無効になるため、秘密鍵そのものとは重みが違います。それでも、他のアプリにコードを渡さないことは、リアルタイムの中継型フィッシングへの対策として意味があります。

7画面の保護

  • 画面共有・録画に映さない：SetWindowDisplayAffinity（WDA_EXCLUDEFROMCAPTURE）を設定します。オンライン会議で画面全体を共有しても、このアプリの画面は映りません（Windows 10 2004 以降）。
  • コードを隠す表示：コードを「••• •••」で表示し、クリックでコピーだけできる表示に切り替えられます（デモで操作できます）。
  • タスクバーのサムネイル、通知、タスクトレイのツールチップには、コードを出しません。
  • 登録後は、秘密鍵や QR コードを画面に再表示しません。別の PC への移行は暗号化バックアップで行います。

8自動ロック

  • 一定時間操作がないとき（既定 5 分、1〜60 分で設定可）。
  • Windows をロックしたとき、スリープ・休止に入るとき、ユーザーを切り替えたとき、リモート接続が切れたとき（SystemEvents.SessionSwitch、PowerModeChanged）。
  • 任意で、最小化したとき・アプリを閉じたとき（タスクトレイ常駐時）。
  • ロックするときは、DEK と復号済みのアカウント一覧をメモリから消し、画面の表示とクリップボードも消します。ロック中は、コードを計算できない状態になります。

9メモリ上の機密情報

C# のメモリは自動で管理されるため、完全に消すことは保証できません。そのうえで、機密情報がメモリにある量と時間を最小にします。

  • 秘密鍵・DEK・パスワードは、消せない文字列（string）ではなくバイト列で扱い、使い終わったらすぐ 0 で埋めます（CryptographicOperations.ZeroMemory）。
  • DEK は、メモリ整理（GC）で別の場所にコピーされないよう、固定した領域（pinned）に置きます。
  • 各アカウントの秘密鍵は、メモリ上でも DEK で暗号化したまま持ち、コードを計算する瞬間だけ復号して、すぐ消します。
  • SecureString は、Microsoft が新規開発での使用を勧めていないため使いません。
  • 手入力欄の文字列など、WPF の内部で一時的に残る部分は消しきれません。設計書とテスト結果に、その範囲を明記します。
  • ロック後にメモリダンプを取り、テスト用の秘密鍵が残っていないことを確かめるテストを行います（15章）。

10ログ・クラッシュ時の情報

  • ログには「何が起きたか」だけを書き、秘密鍵・コード・パスワード・アカウント名・QR の内容は書きません。
  • 秘密鍵を持つクラスは、ToString() で中身を出さないようにします（テストで確認済み）。
  • エラーメッセージに入力値を含めません。例えば、シークレットキーの書式エラーで、入力した文字そのものを表示しません（テストで確認済み）。
  • Windows エラー報告がクラッシュ時にメモリダンプを作らないよう設定します（WerAddExcludedApplication など）。
  • 利用状況の送信（テレメトリー）は行いません。

11保存・バックアップ・復元

保存

  • 保存先は %LOCALAPPDATA%\TotpVault\ です。移動プロファイルでサーバーに複製されないよう、Roaming ではなく Local に置きます。
  • 同じフォルダーの一時ファイルに書き、ディスクへの書き込み完了を待ってから置き換えます。保存中に電源が落ちても、ファイルが書きかけになりません。1世代前のファイルを .bak として残します（暗号化されたまま）。

バックアップ

  • マスターパスワードとは別のパスワードで、同じ形式で暗号化します。マスターパスワードが漏れても、外に保管したバックアップは守られます。
  • 初回設定の最後と、アカウントを追加した後に、バックアップを案内します。最後のバックアップからの日数を画面に表示します。
  • バックアップを作った直後に、そのファイルを読み直して復号できることを確かめます（壊れたバックアップに気づかない事故を防ぐ）。

復元

  • 「置き換え」と「追加（統合）」を選べます。追加のときは、同じアカウントを重複して登録しないよう判定します。
  • バックアップファイルと保管庫ファイルを取り違えた場合は、その旨を表示します。

12TOTP と QR コード

  • RFC 6238（TOTP）と RFC 4226（HOTP）どおりに実装し、SHA-1・SHA-256・SHA-512、6桁・8桁、30秒・60秒に対応します。時刻は 64bit で扱い、2038年問題の影響を受けません。
  • QR コードの中身（otpauth://totp/…）を解析します。空白の表記ゆれや、区切り文字の符号化（%3A）にも対応します。
  • QR コードの中で、2か所に書かれたサービス名が食い違う場合は、なりすましの可能性として警告します。
  • シークレットキーの手入力では、小文字・空白・ハイフンを自動で無視し、使えない文字（0・1・8・9 など）は理由を示してお知らせします。

QR コードの取り込み方

PC では、QR コードはブラウザの画面に表示されることがほとんどです。カメラよりも、次の方法が便利です。

  1. クリップボードの画像から読み取る：Win+Shift+S で切り取った画像を、そのまま貼り付けます（デモで操作できます）。
  2. 画像ファイルから読み取る／URI やシークレットキーを手入力する。
  3. 画面から読み取る（第2段階）：ボタン1つで、画面に表示中の QR コードを探して読み取ります。

読み取った画像はファイルに保存せず、読み取り後すぐにメモリから消します。

13通信しない設計と時刻

  • アプリに通信の機能を持たせません。自動更新もしません（更新は、署名付きの新しいインストーラーで配布します）。
  • 通信していないことは、Windows ファイアウォールやネットワークの監視ツールで、利用者が確かめられます。
  • 時刻のずれ（第2段階）：TOTP は PC の時刻をもとに計算するため、時計がずれると正しいはずのコードが拒否されます。アプリは通信せずに、Windows の時刻同期の状態（最後に同期した日時）を読み取り、長く同期していない場合は画面でお知らせします。

14インストーラーと署名

  • 社内の PC へ一括配布する場合は MSI（WiX、Intune やグループポリシーで配布可）、個人の PC へ配る場合は Inno Setup を提案します。どちらも、管理者権限なしでユーザーごとにインストールできる形にします。
  • アンインストールのときは、保管庫ファイルを消すかどうかを確認します（誤って消すと、2段階認証を失うため）。
  • コード署名：署名がないと、インストール時に Windows の警告（SmartScreen）が出ます。認証アプリで警告が出ると、利用者は不安になります。日本の法人では、認証局の OV コード署名証明書（年に数万円程度）が現実的です。証明書の取得は御社の名義で行う必要があるため、ご判断をお願いします。

15テストの方針

  • 自動テスト：RFC に載っている正解値（SHA-1/256/512・8桁・2603年の時刻を含む）、暗号化と復号、改ざんの検知、パスワード変更、バックアップの取り違え、壊れにくい保存。試作の段階で 91 件に合格しています。
  • 実機での確認：Windows 10 22H2 と Windows 11 で、表示倍率 100・150・200%、ダークモード、ロックとスリープの検知、クリップボード履歴と画面共有での映り込みを確かめます。
  • 主要サービスとの照合：テスト用のアカウントで、実際のサービスの 2段階認証の登録とログインが通ることを確かめます。
  • 機密情報が残らないことの確認：操作後のログ・設定ファイル・ロック後のメモリダンプを検索し、テスト用の秘密鍵が見つからないことを確かめます。
  • 結果は、項目・手順・結果の表にまとめて納品します。

16守れること・守れないこと

守れること

  • PC・ディスクの盗難や紛失で、保存ファイルを読まれること（強いマスターパスワードの場合）
  • 保存ファイル・バックアップの改ざん（検知して開かない）
  • 席を離れた間の覗き見や操作
  • 画面共有・録画への映り込み
  • クリップボードの履歴・クラウド同期にコードが残ること
  • ログやエラー表示から秘密鍵が漏れること
  • 保存中の電源断によるファイルの破損

守れないこと（正直にお伝えします）

  • ロック解除中に、同じ Windows ユーザーの権限で動くマルウェア（画面・メモリ・キー入力を読めるため）。ウイルス対策などの、OS 側の対策が前提です。
  • 管理者権限を持つ攻撃者による攻撃
  • 推測されやすいマスターパスワード（強さの表示で減らせますが、防ぎきれません）
  • キーロガーによるマスターパスワードの盗み見（Windows Hello の併用で、入力の回数を減らせます）
  • .NET が内部で一時的に作るコピーを、完全に消すこと（範囲を最小にします）
  • ページファイル・休止ファイルへの書き出し（BitLocker の利用をお勧めします）
  • 古い保管庫ファイル（以前のコピーや .bak）への差し戻し（正しいパスワードで作られた本物のファイルのため、改ざんとしては検知できません。保管庫ファイルの置き場所への書き込みを防ぐ、OS 側の権限管理が前提です）
  • マスターパスワードを忘れた場合の復旧（設計上できません）

運用上のご注意：パスワードと 2段階認証のコードが同じ PC にそろうと、「PC を持っている人」だけでログインできる状態になり、2段階認証の効果が弱まります。社内の重要なアカウントは、スマホなど別の端末と併用するといった運用ルールも、あわせてご検討ください。

複数の PC 間での同期は、通信が必要になり攻撃の入口が増えるため、対象外とすることを提案します。必要な場合は、暗号化バックアップの受け渡しで対応できます。

18ご確認したい点

  1. 利用の形：社内で使う（何名、配布方法）か、製品として一般に配布するか。必要な作り込み（署名、インストーラーの形式、更新方法）が変わります。
  2. 対象の OS：Windows 10 は 22H2 を前提にしてよいか。
  3. コード署名証明書：御社でお持ちか、取得のご予定があるか。
  4. Windows Hello：第1段階に含めるか、第2段階とするか。
  5. バックアップの保存先：PC 内、USB メモリ、社内の共有フォルダーなど。
  6. 他の認証アプリからの移行が必要か。
  7. 社内利用の場合、利用記録（いつ、どのアカウントのコードを使ったか）が必要か。
